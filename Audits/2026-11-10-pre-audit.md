## Summary

No critical, high or medium finding. **One low is confirmed** in the contracts, reproduced by a passing test. **Three leads in the worker** are real in the code and reproduced locally, but each needs one fact that only the deployment shows (how Filebase answers under load, the memory limit of the Workers runtime), so they carry no severity. All three have a small code fix, and the worker is not deployed yet: the fixes can go in before it is.

The worker's proof held: a landed call is the only way to get a CID pinned, the CID position of every function matches the contract, and the address charged is the one that authorized the call. The contract areas the round examined held too.

### H-1 (Low): any maintainer can fill a member's record

A member has one storage entry, and its `projects` list holds one item per project that gave it badges. `set_badges` checks only that the caller maintains the project it names (`contract_membership.rs:184`), then appends to the member's list with no consent and no cap (`:228`) and writes the whole entry back (`:273`). Registering a project costs 5 XLM (`contract_versioning.rs:11`) and names are free.

A test with 510 attacker projects brought a victim's record to 65,396 bytes. A maintainer of an unrelated project then could not give the victim a badge: the entry would be 65,624 bytes, over the 65,536 limit, and the call failed. The victim's weight in that project stays 1. The code's answer is that a member can remove a project from its own record (`:172`), one entry per call. The test shows this does not hold against the attacker: the member removes one entry, the attacker adds the same project again at no new cost, and the legitimate call fails again. A legitimate call that lands right after a removal succeeds.

Impact is limited: it is pure harm with no gain, it costs 2,550 XLM of collateral that is not returned (paid once, usable against every member), no funds or votes are affected, and existing badges keep working. The test environment enforces the entry limit of the SDK's mainnet snapshot; a different live value changes only the number of projects.

**Fix:** keep a member's badges for a project in an entry of their own, keyed by project and member, so a project's maintainers write only their project's entry and `get_max_weight` reads one entry. A cap on the list does not help: it makes the fill cheaper. If the single record stays, require the member's authorization to add a project that is not yet in its record. Regression test: the 510-project fill, then a badge from another project succeeds.

### N-07 (lead): another address's quota can be spent by a stranger

The worker has no login. The quota is charged to the address named in the landed call (`index.ts:153`, `:435`), and anyone can send the request: the transaction hash is public, and so is the content of every CID once it is uploaded. The only thing that makes such a replay free is the early return when the bucket already pins the CID (`:431`). That check fails open: `pinStatus` answers "unknown" on a timeout, a non-JSON body, 401, 403, 429 or a 5xx (`:246-273`), and the handler then reserves quota for the recorded address and uploads again. The README and a test state that an unclear answer counts as "not pinned"; neither says that a stranger's replay is then charged to the recorded address.

The size charged is the size of the CAR the caller sent, and `verifiedRoot` accepts a CAR that repeats a block: its link map is keyed by CID and the reachability test compares de-duplicated sizes (`car.ts:36`, `:87`). One small CID can therefore be charged close to 10 MB.

A test with the real handler, CAR check and quota object (Filebase and the RPC stubbed), with `pin/ls` answering 503:

- a 65,835-byte directory padded to 10,426,685 bytes passed the check and was charged at that size;
- eleven replays of a victim's earlier `update_member` transactions reached 104,857,287 of the 104,857,600 bytes of its day, and the victim's own 1 KB upload then got 429;
- fifty small replays filled the 50-CID count the same way;
- with `pin/ls` answering "pinned", nothing was charged and the victim's upload succeeded.

A CID already counted in the current window is free, so the replay needs the victim's CIDs of earlier days that the RPC still serves. The victim's transactions keep landing while its files are refused for up to 24 hours.

**Conditions the source cannot settle:** how often Filebase `pin/ls` fails or throttles for the operator's token, and whether an outsider can cause it (each replay answered "pinned" is free, so a caller can wait for a failure); how far back the configured RPC serves `getTransaction`; whether Filebase `dag/import` accepts a CAR with repeated blocks (a refused import releases the reservation).
**Fix:** refuse a CAR that holds the same block twice (compare the number of blocks read with the size of the link map), and when the pin check answers "unknown", accept only a transaction that landed recently (the RPC answer carries its time) and answer 503 for an older one. Regression test: the eleven replays with `pin/ls` down leave the victim's quota untouched.

### N-08 (lead): `/health` is unrated and one throttled answer reads as "down"

`GET /health` returns before the rate limit (`index.ts:329-338`, limit at `:368`). `filebaseLive` stores the result only after the probe returns (`:278-285`), so every request that arrives while a probe is in flight starts its own `pin/ls` call with the operator's token. A test with 50 concurrent requests during one probe made 50 Filebase calls and no rate-limit check. A single 429 from `pin/ls` then gave 503 at 0 s and at 29 s, and 200 again at 31 s. While `/health` answers 503 the dApp refuses to sign any write with files (`dapp/src/utils/ipfsFunctions.ts:241`).

The upload path adds to the same budget: every request with a copied hash calls `pin/ls` once, limited to 30 a minute per address.

**Conditions the source cannot settle:** Filebase's rate limit for the token and whether `dag/import` shares it; what Cloudflare puts in front of the route.
**Fix:** keep the pending probe and let concurrent requests await it; put `/health` behind the same rate limit; count a 429 as "Filebase answers" for the health answer, or shorten the time a failed probe is kept.

### N-09 (lead): memory needed to decode a CAR under the cap

Two steps need much more memory than the CAR's size. Both come after the proof check, which a caller passes with any copied public hash and its CID.

- The body's `car` field is decoded with `Uint8Array.from(atob(...), ...)` and its length is checked afterwards (`index.ts:410-414`). Under Node with the heap capped at 128 MB, a 10 MiB CAR ran out of memory; it passed at 256 MB. An honest upload near the cap takes the same path.
- `verifiedRoot` turns every link of a DAG-PB block into a CID object and a string before any link is resolved (`car.ts:63-66`). Blocks are capped at 2,048, links are not: one 9.96 MB block with 262,000 links ran out of memory at 256 MB before it was refused.

Both peaks are transient, and growth is linear in the input.

**Conditions the source cannot settle:** whether these peaks pass the 128 MB limit of a Workers isolate under Cloudflare's build of V8, and whether passing it fails only that request or the others on the isolate too. Node is not that runtime.
**Fix:** check the length of the base64 string against the cap before decoding, decode into an array allocated once, and cap the links of one block and of the whole CAR. Then one run under `wrangler dev` with a 10 MB upload settles it either way.

## Entry points and trust

**Worker.** Every POST, on any path, is the upload; `GET /health` and `OPTIONS` are the only other routes. CORS headers are withheld from other origins but nothing is refused by origin: a non-browser client is not blocked, by design. The order of checks is: rate limit, capped body read, the transaction proof, base64 decode, the CAR check, the pin check, the quota, the upload. Operator credentials go only to fixed Filebase and Pinata hosts.

**Contracts.** By gate:

| Gate | Entry points |
|---|---|
| Anyone (own authorization only) | `add_member`, `update_member`, `register` (5 XLM), `create_proposal` (5 XLM), `vote`, `tansu-executor::run`, `registry-tansu-manager::trigger` |
| A project maintainer, alone | `update_config`, `commit`, `set_evidence`, `set_sub_projects`, `set_attestation_threshold`, `attest`, `set_badges`, `set_nqg_contract`, `anonymous_voting_setup`, `remove_vote`, `veto`, `revoke_proposal`, `execute`, the conflict-of-interest list |
| One admin | `pause`, `set_executor`, `propose_upgrade`, `approve_upgrade`, cancel in `finalize_upgrade`, `revoke_proposal` on any project (also while paused) |
| Admin threshold and timelock | accept in `finalize_upgrade` |
| Worth knowing | `revoke_attestation` checks only the attester's authorization, so a former maintainer can still revoke within the window; `set_badges` with an empty list lets a member remove a project from its own record |

Authority is always `require_auth` on the address the caller names, followed by a membership check against a list read from storage (`lib.rs:283-298`, `contract_tansu.rs:340-347`). Only temporary ballots have their lifetime extended; every other entry is persistent or instance and is never extended by the contract.

| Threat | Worker | Contracts |
|---|---|---|
| Spoofing | The proof is a landed call; the charged address is the one that authorized it. Held | `require_auth` on every writer. Held |
| Tampering | A CAR must hash, block by block, to the recorded CID. Held | Typed keys; outcome calls run through an executor that holds nothing. Held |
| Repudiation | One log line only (a failed Pinata pin) | Every writer emits an event, except the lazy activation of pending governance and the finality latch |
| Information disclosure | No secret reaches an error message. Held | All data is public by design |
| Denial of service | N-07, N-08, N-09 | H-1; lists a maintainer grows in its own project |
| Elevation of privilege | None found | None found |

## What was attacked and held

**Worker**

- **The proof.** Each of the seven functions in `CID_CALLS` matches the contract's signature: the CID index is the argument the contract stores, and the address at index 0 is the one each function makes authorize. A Soroban transaction holds one host-function operation and a failed one fails the transaction, so `SUCCESS` means the call completed and stored the CID. Fee bumps are unwrapped and a relayer's source account is never read. A call made from inside another contract does not qualify.
- **Replay.** A copied hash uploads only content that hashes to the recorded CID, and it is free once the bucket pins it (N-07 is the case where the bucket does not say so).
- **Quota mechanics.** Reserve and release pair on the Filebase failure path, the Durable Object serializes requests for one address, and a retry of a counted CID is free.
- **CAR check.** SHA-256 only, identity CIDs refused, CIDv0 and CIDv1 forms of the root normalised, trailing bytes after a CARv1 refused: no CAR was found that passes while Filebase would import something else.
- **HTTP.** The origin pattern is escaped and anchored; the CID reaches a Filebase URL only after it equals the CAR's root; retries and timeouts are bounded per request.
- The vulnerability hunt rejected nine ideas here, among them a forged RPC answer (the RPC is the operator's choice), a call that succeeds without storing its CID (none does), and a race between two uploads of one CID (the second is free and the bytes are identical).

**Contracts**

- **Attestation pruning.** At the 25-attestation cap `attest` drops only attestations of addresses that are no longer maintainers (`contract_versioning.rs:806-816`), which the finality count already ignores. It cannot make a target final or not final, it does not touch the latch, and it cannot keep a current maintainer from attesting, since maintainers are capped at 25 too.
- **The manager's chain.** `trigger` authorizes `outcomes[0]` and `execute`, in the same transaction, passes that stored contract, function and arguments to the executor: the two match field by field. `trigger` requires exactly one outcome, so a rejected or cancelled result selects an empty slot and the manager's authorization is unused. A stranger calling `trigger` or `executor.run` gains nothing. This was read from source and the existing test, not run in a new one.
- **Getters and lists.** `get_projects` pages, evidence, attestations and sub-projects are bounded; the conflict-of-interest list is written only by the project's maintainers. With a member record filled by 600 projects, `get_max_weight` cost 5.2 M instructions and `vote` 13 M: no exhaustion.
- **Soroban checklist.** Twenty items: authority from storage, one-time init, gated upgrade, checked math with `overflow-checks` on, validated inputs, typed keys, nothing in temporary storage that an expiry would undo (voters and tallies are persistent, so an expired ballot allows no second vote), no permission tied to an expiry, events, stable error values, pause. No item crossed a trust boundary.
- The vulnerability hunt rejected seven ideas on the proposal lifecycle, among them unlimited proposals (each pays a deposit), a failing outcome that blocks `execute` (maintainers veto or revoke), and one maintainer replacing the anonymous key (a documented power).

## Hardening notes

Not findings; each is a code change you can take or leave.

**Worker**

- The Filebase answer is accepted when its text merely contains the CID, and the check swallows its own mismatch error (`index.ts:473-485`).
- A CARv2 file with unreferenced bytes after its data passes the CAR check.
- `release` removes a CID that another request of the same address still holds, and if `release` itself fails the reservation stays.
- The envelope the RPC returns is not hashed and compared with the requested hash.
- A request with a random hash costs up to four RPC polls and about 7 s; the rate limit is per location and an IPv6 client can move within its prefix.
- The quota is per address and addresses are cheap: the real bound is one landed transaction per CID. A daily ceiling per environment would bound the total.
- A deployment without `--env` has no variables: `MAX_CAR_BYTES` is then not a number, both size comparisons are false and the body is read with no cap before the proof is checked (`index.ts:368-386`; read from source, not run). The deploy scripts always pass `--env`. Refuse a request when the variables are missing.
- The preview-origin wildcard accepts letters and hyphens; digits are enough.

**Contracts**

- `refund_collateral` panics when the proposer can no longer receive, so a proposer keeps its own proposal from being executed or vetoed; a failing outcome leaves a proposal active, and a project whose only maintainer is the manager cannot clear it.
- `trigger` cannot run an anonymous proposal (it passes no tallies) and reports an empty outcome list as "multiple outcomes".
- The manager imports `tansu.wasm` by path with no hash.
- `set_executor` is immediate and unchecked for one admin; a timelock would match the upgrade flow.
- A token-weighted proposal reads balances at vote time with no snapshot; `decimals()` and `balance()` are not `try_` calls, so a token that traps blocks voting.
- `get_nqg` panics on a WASM-hash mismatch, which blocks every vote of the project until a maintainer resets the reference.
- A maintainer removed and added again loses its earlier attestation when the list is pruned; `get_projects` past the last page panics.
- `Member.meta`, outcome arguments and the badge lists are not bounded. Nine proposals with very large arguments may make one `get_dao` page unreadable (the vulnerability hunt left this open: it depends on network limits).
- Scout is not run in CI and cannot run offline; clippy runs with `-Dwarnings`.

## Not covered

- **Contracts outside the three areas.** The contract source is identical to the last contracts round, so admin and upgrade, membership, project registration, voting, the anonymous tally and veto were not hunted again, and the two open contract items of that round (F-07, F-08) were not re-verified.
- **The Workers runtime and Filebase.** N-07, N-08 and N-09 each wait on a fact about them. Tests ran under Node with `fetch` stubbed.
- **The manager's nested authorization** was not exercised by a new test.
- **Two ideas of the vulnerability hunt** did not get a test of their own: both are the subject of N-07 and N-09.
- The dApp (including the worker's client), the events service, CI and anything that depends on the live network.

## Method and limits

Reviewers worked on a frozen copy of the source and ran tests only inside an offline sandbox (no network, writes only to their own scratch). The worker's own 47 tests pass in it. Contract results come from the Rust test environment and the SDK's mainnet-limit snapshot, so they are lower bounds for the live network. A lead is an item whose path is shown in the code and reproduced locally but whose effect depends on a named fact outside the source; it gets no severity until that fact is known. The tests behind each item are kept with the run, not in this repository.
